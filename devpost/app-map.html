Project code tour · ExamPilot

From course notes to grounded practice

ExamPilot is a small Flask application that turns a learner’s own course material into one practice question, then evaluates an answer against that same source. This map follows the code path and calls out the boundaries that matter most.

2. The three API contracts

POST /api/material

Multipart form field: file. Success returns {"material": "extracted text"}. The file-size cap is 10 MB; extracted text is not capped by word count. Scanned PDFs are not OCR’d.

POST /api/question

{"material": "student's notes", "topic": "Process Control Block"}

A supported result contains status, question, explanation, and an exact evidence_excerpt. An unsupported topic returns an explanation and no fabricated question.

POST /api/evaluate

{"material": "student's notes", "topic": "Process Control Block", "question": "What is stored in a PCB?", "answer": "My answer..."}

The response label must be Correct, Partially correct, or Needs improvement. Feedback points can have an empty evidence excerpt, but the UI explicitly labels such points as lacking a supporting passage.

4. Design and safety principles

  • Source boundary: the supplied course material is the only intended study source; the app does not use web search or a hosted AI API.
  • Evidence check: every non-empty returned excerpt must be a literal substring of the original source. This proves the quote is present, not that the model’s interpretation is necessarily correct.
  • Untrusted input: notes and answers are passed as data, separate from trusted application instructions.
  • In-memory session: the app does not save uploaded files or keep a study history; refresh/close clears the browser session.
  • Bounded uploads: supported file types are TXT, Markdown, text-based PDF, and DOCX, up to 10 MB. Scanned PDFs and OCR are out of scope.
  • Recoverable failures: question generation still rejects unusable model output rather than inventing a question. If answer evaluation fails or cannot pass evidence validation, the app switches to an explicitly disclosed, conservative word-match fallback with exact source excerpts; it never labels fallback feedback “Correct.”

Important limitation: local model output can still be wrong or unhelpful even when its quoted evidence exists in the notes. The learner should compare the explanation and feedback with the source. The app is a study aid, not an authority on course content.

6. A project-grounded practice to reuse

When a large-note request fails, debug the smallest boundary first instead of weakening the grounding checks:

  1. Check the browser Network panel for the /api/question status and response body.
  2. Check the Flask terminal for the safe diagnostic fields operation, failure_class, and elapsed time—without printing course notes or full prompts.
  3. Confirm that select_relevant_context() returns bounded context and that SelectedContext.maps_to(original_material) is true.
  4. Verify that the local Ollama model is available with ollama list and test a short supported topic first.
  5. Only then retry with the large notes. Preserve exact-evidence validation; do not accept a paraphrase as a source quote.

7. Transfer reflection

Use these prompts to carry the engineering lesson into another project or subject:

  • Which data is trusted application instruction, and which data is user-supplied input that must be treated as untrusted?
  • What can a test prove mechanically, and what still needs a real person to inspect the experience?
  • If this pattern were adapted to another course, which source boundary and evidence checks must remain unchanged?
  • What single observable result would convince you that the feature works for a learner, rather than merely compiling?

For ExamPilot, the transferable lesson is to test the smallest failing boundary, preserve evidence validation, and never upgrade an unobserved behavior to “verified.”
